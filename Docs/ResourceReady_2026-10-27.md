# 리소스 적용 전 최소 플레이 점검

기준일: 2026-10-27, 한국 시간.

> 2026-11-02 후속: 일반 배경·기관차·객차 2종을 적용하고 Windows 파일을 갱신했다. 폐역 배경과 추가 UI는 아직 미적용이다. 최신 적용 결과는 [CoreArt_2026-11-02.md](CoreArt_2026-11-02.md)를 참조한다.

> 2026-10-28 후속: 사용자가 제공한 Neo둥근모 Pro를 Unity와 Windows 빌드에 적용했고 FHD/HD를 검증했다. 아래의 글꼴 미적용 설명은 2026-10-27 당시 상태다. 최신 글꼴 상태는 [Font_2026-10-28.md](Font_2026-10-28.md)를 참조한다.

대상은 v0.5의 ‘이번에 제작할 최소 플레이’와 이후 채팅에서 합의한 시험 규칙이다. 장기 밸런스·최종 엔딩·새로운 기획을 완성했다는 뜻이 아니다. 이전 구현 상세는 `AgreedRun_2026-10-26.md`를 참조한다.

## 이번 보완

- 기존 자원·탐사·위험·생존자·실패 규칙은 유지했다.
- `MinimalRunPresentation`에 일반 구역 배경, 폐역 배경, 기관차, 객차 1, 객차 2를 연결하는 항목을 마련했다.
- 그림이 없으면 임시 도형을 표시한다. 구역에 따라 임시 배경색도 바뀐다. 그림이 있으면 흰색으로 표시해 원래 그림 색을 유지하고, 기차 그림은 원본 비율을 보존한다.
- 배경 영역은 FHD 기준 `(0,240)`에서 `1920×340`, 기차 각 칸은 약 `470×180`이다. 현재 임시 화면에서의 교체 위치이며 최종 제작 규격을 확정한 것이 아니다.
- 생존자 선택 중 오른쪽 위의 임시 화면 안내를 숨겨 상태 보기 버튼과 겹치지 않게 했다.
- `MinimalRunScreen`에 `Ui Font` 항목을 추가했다. 글꼴을 넣으면 전체 임시 UI에 적용하며, 비워 두면 기존 Windows 맑은 고딕을 사용한다.
- 실행 파일은 Windows 창 모드, 기본 FHD로 설정했다. 코드·씬·설정의 이전 파일은 채팅 작업 폴더 `.work/before-resource-ready/`에 보존했다.
- 실행 파일 캡처에서 탐사 보너스의 마지막 줄 잘림을 확인해 해당 정보의 글자 크기와 높이를 보완했다. 최소 플레이에서 사용하지 않는 2D 후처리를 끄고 관련 셰이더 경고도 제거했다.

## 그림을 넣는 순서

먼저 Play를 끈다. 실행 중에 바꾼 항목은 Play를 끄면 원래대로 돌아갈 수 있다.

1. Project 창에서 `Assets` 안에 원하는 리소스 폴더를 만들고 PNG를 끌어 넣는다. Project는 프로젝트의 파일 목록이다.
2. PNG를 선택한다. Inspector의 `Texture Type`을 **Sprite (2D and UI)**로, 픽셀 아트라면 `Filter Mode`를 **Point (no filter)**, `Compression`을 **None**으로 설정하고 **Apply**를 누른다. Sprite는 Unity에서 2D 그림으로 사용하는 형식이다.
3. Hierarchy에서 **MinimalRunCanvas**를 선택한다. Hierarchy는 현재 씬에 배치된 대상 목록이다.
4. Inspector의 **Minimal Run Presentation**에서 다음 항목에 PNG를 끌어 놓는다.

| Inspector 항목 | 용도 |
|---|---|
| General Background | 일반 구역 배경 |
| Station Background | 폐역 배경 |
| Locomotive | 기관차 외관 |
| Carriage One | 객차 1 외관 |
| Carriage Two | 객차 2 외관 |

5. 배경은 표시 영역에 맞춰 채우므로 현재 영역과 비슷한 가로세로 비율을 사용한다. 기차 그림은 투명 배경으로 준비하면 배경이 보인다. 객차 두 칸에 같은 그림을 연결해도 된다.
6. 같은 대상의 **Minimal Run Screen > Ui Font**에 확보한 Neo둥근모 Pro 글꼴을 넣는다. 글꼴 파일을 Project에 넣은 뒤 끌어 놓으면 된다. 파일과 사용 조건 확인은 아직 필요하다.
7. **Ctrl+S**로 씬을 저장한 뒤 Play를 눌러 시작한다. 일반 구역에서 폐역으로 바뀔 때 배경이 바뀌는지 확인한다. 파일을 새로 넣은 뒤에는 실행 파일도 다시 빌드해야 반영된다.

연결된 화면 항목과 기존 버튼의 On Click 이벤트는 유지한다. 그림만 교체하는 경우 게임 규칙 코드를 수정할 필요가 없다. 그림 구도나 버튼 배치를 크게 바꾸면 Rect Transform(화면 안의 위치·크기) 조정은 필요할 수 있다.

단색 UI는 현재 범위에서 그대로 쓸 수 있다. 인물별 초상화·아이콘·애니메이션·이펙트·사운드는 이 최소 플레이를 위해 추가 제작할 필수 리소스가 아니다. 기존 v0.3의 그림 11장 목록을 새 제작 목록으로 사용하지 않는다.

## 실행 파일과 다시 빌드하기

Windows 실행 파일: `Builds/WindowsPrototype/YeolgukTrain.exe`.

`YeolgukTrain.exe`만 따로 옮기면 실행되지 않는다. 같은 폴더의 `YeolgukTrain_Data`, `UnityPlayer.dll` 등 생성된 파일을 함께 보관한다. 창 닫기 또는 **Alt+F4**로 종료한다.

그림 적용 후 Unity 상단 **File > Build Profiles**를 연다. Windows의 Scene List에 **PrototypeMain**이 활성화되어 있는지 확인한 다음 **Build**를 누른다. 개발 중인 검사 도구를 계속 사용하려면 **Development Build**를 켠다. 이는 개발용 진단 정보를 포함하는 빌드라는 뜻이며, 일반 실행에 자동 검사 화면이 추가되는 것은 아니다.

## 개발용 실행 검사

`Assets/Scripts/MinimalRunPlayerVerification.cs`는 Editor 또는 Development Build에서만 실행할 수 있다. 실행 인자 `--verify-minimal-run <결과 폴더>`를 명시했을 때만 검사한다. 일반 실행에서는 동작하지 않는다. 외부 네트워크나 원격 조작 서버를 켜지 않는다.

검사는 실제 빌드 씬에서 UI의 맨 위 클릭 대상과 버튼 이벤트를 확인한다. 시작·폐역 진입·생존자 선택·창 숨김/복원·수용·10명 파견·자원 입고·실패·타이틀·새 RUN·거절 경로를 수행한다. 오래 걸리는 날짜 진행은 실제 시간을 기다리는 대신 게임 규칙 함수에 시간을 전달한다. 따라서 실제 65분 플레이나 사람의 마우스 조작과 구분한다.

## 검증 결과

직접 확인한 것:

| 검사 | 결과 |
|---|---|
| 최종 코드 컴파일 | 오류 0, 경고 0 |
| 기존 게임 규칙 | 25/25 통과 |
| 임시 Sprite로 연결 항목 검사 | 배경·기차 3칸·원본 비율·임시 문구 숨김·빈 항목 복원 통과 |
| Unity Play 버튼 경로 | 시작→첫 폐역→숨김/재표시→수용→사건 중복 방지→실패→타이틀→새 RUN 통과 |
| Windows x64 개발 빌드 | 성공, 빌드 오류 0 |
| 같은 최종 실행 파일 FHD 검사 | 1920×1080, 14개 흐름 확인, 종료 코드 0 |
| 같은 최종 실행 파일 HD 검사 | 1280×720, 14개 흐름 확인, 종료 코드 0 |
| 실제 실행 파일 화면 | 타이틀·일반 구역·선택창·숨긴 상태·탐사·실패 캡처 확인. 탐사 보너스 마지막 줄 잘림 보완 후 재확인 |
| Windows 마우스 입력 | computer-use 스킬의 네이티브 입력으로 실행 파일의 시작 버튼→관리 화면 확인 |
| 마지막 Play 세션 Console | 실제 집계 오류 0, 경고 0. 과거 빌드 실패 기록의 누적 집계와 구분 |

Windows 빌드 경고 1개는 Pipeline 조작 서버가 플레이어 빌드에서 비활성화되어 있다는 안내다. 실행 파일의 게임 오류가 아니다. 실행 파일은 Unity Editor 연결 없이 동작한다.

첫 빌드에서는 메모리에서 실행한 1회 제작 도구의 어셈블리 경로를 Unity가 변환할 때 `Illegal byte sequence` 오류가 발생했다. 코드 재로딩으로 임시 어셈블리를 제거한 뒤 빌드가 성공했다. 이어 실행 전용 조건과 사용하지 않는 후처리 설정을 보완했고, 최종 빌드를 두 해상도에서 검사했다. 제작 도구를 `run_script`로 실행한 직후 같은 오류가 재발하면 Unity를 종료했다가 동일 프로젝트를 다시 열어 빌드한다. `PrepareResourceReady` 같은 1회 제작 도구를 반복 실행할 필요는 없다.

사용자 확인으로 구분할 것:

- 이전 사용자 응답에서 Unity의 선택창 숨김·재표시와 시간·식량·연료 정지가 정상임을 확인했다.
- 이번에는 최종 아트와 Neo둥근모 Pro 파일이 없으므로 실제 리소스를 적용한 외관·글꼴 가독성까지 검증한 것은 아니다.
- 65분을 실제로 기다리거나 다른 PC에서 실행하지 않았다. 2~3분 발표 리허설과 장기 밸런스 검증도 별도다.

검증 근거는 채팅 작업 폴더 `Evidence/ResourceReady-2026-10-27/`에 있다. FHD와 HD 하위 폴더의 `player-result.txt`와 PNG, `MinimalRunChecks.txt`, `MinimalRunResourceChecks.txt`, `MinimalRunUIChecks.txt`, `ResourceReadyBuildReport.json`을 보존했다.

최종 Windows 실행 파일 SHA-256: `AC52A872FC9DD41F49F03A796A85AF890447405B28CC0167EEF7679267FF04EB`. 실제 게임 코드는 함께 있는 `YeolgukTrain_Data` 폴더에도 포함되므로 이 실행 파일만 따로 배포하지 않는다.

Unity가 빌드 중 갱신한 URP의 셰이더 선별 정보와 Input System 사전 로드 항목도 포함되어 있다. 기존 변경을 보존했으며 이번 작업에서도 커밋·원격 업로드를 하지 않았다.

## 다음에 필요한 것

- 배경과 기차 그림, 지정 글꼴 확보 및 연결.
- 최종 리소스를 적용한 뒤 읽기 쉬운지와 구도가 맞는지 다시 확인하고 실행 파일 재생성.
- 2~3분 발표에서 어디까지 보여주고 마칠지 정해 리허설. 현재는 생존자 선택과 재출발까지 보여주고 설명을 끝낼 수 있으며, 별도의 성공 엔딩은 만들지 않았다.
- 시험 수치의 재미와 밸런스 조정은 이후 피드백으로 진행한다. 이번 완료 기준에 장기 생존 밸런스를 포함하지 않는다.

## 2~3분 발표 동선 예시

새로운 게임 규칙을 추가하지 않고 현재 값으로 보여줄 수 있는 순서다. 실제 소요 시간은 설명 속도와 사고 발생 여부에 따라 달라진다.

1. 타이틀에서 시작하고 출발한다. 일반 구역·정차·하루 식량·연료를 설명하면서 60초 운행한다.
2. 폐역으로 바뀌면 정차하고 3~5명을 파견한다. 6~9초 정도 자원 증가와 위험도를 보여준 뒤 귀환한다. 사고로 2명 이하가 되면 강제 귀환으로 이어진다.
3. 생존자 선택창에서 상태 보기를 눌러 멈춘 수치를 확인한다. 다시 열어 수용 또는 거절한다.
4. 수용했다면 늘어난 인원과 하루 식량 필요량을 설명한다. 인원 손실이 없고 전체 11명이라면 10명 파견도 가능하다. 사고가 발생했다면 실제 남은 인원 범위에서 선택한다.
5. 귀환해 자원 입고 후 재출발하는 것으로 발표 설명을 마친다. 게임에 별도의 성공 종료를 추가하지 않는다.

하루가 5분이므로 이 동선 안에서 배급이나 굶주림 실패를 자연스럽게 보여줄 수는 없다. 실패 설명이 필요하면 별도로 준비된 실패 화면 캡처를 사용하거나 Editor의 `Preview Failure Screen`을 사용한다. 실제 짧은 플레이로 굶주림 7일을 달성했다고 설명하지 않는다.
